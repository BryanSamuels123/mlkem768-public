# Parameters, hash functions, and the §3.3 implementation requirements

FIPS 203 §3.3, §4.1, §8. The cross-cutting material that every other note depends on.

---

## Parameter sets — Table 2 (§8, p. 48)

| | n | q | k | η1 | η2 | du | dv | required RBG strength (bits) |
|---|---|---|---|---|---|---|---|---|
| ML-KEM-512 | 256 | 3329 | 2 | **3** | 2 | 10 | 4 | 128 |
| **ML-KEM-768** | **256** | **3329** | **3** | **2** | **2** | **10** | **4** | **192** |
| ML-KEM-1024 | 256 | 3329 | 4 | 2 | 2 | **11** | **5** | 256 |

`n = 256` and `q = 3329` are constants across all parameter sets; the other five vary.

Note ML-KEM-512 is the only set with `η1 ≠ η2`. Code that conflates them will be correct
for 768 and 1024 and wrong for 512 — relevant because spec §1 requires other parameter
sets be a parameter change, not a rewrite.

## Sizes — Table 3 (§8, p. 48)

| | ek | dk | ciphertext | shared secret |
|---|---|---|---|---|
| ML-KEM-512 | 800 | 1632 | 768 | 32 |
| **ML-KEM-768** | **1184** | **2400** | **1088** | **32** |
| ML-KEM-1024 | 1568 | 3168 | 1568 | 32 |

Derived: `ek = 384k + 32`, `dk = 768k + 96`, `ct = 32(du·k + dv)`.

`ζ = 17` is the primitive 256th root of unity mod q.

## Hash functions and PRF (§4.1)

```
H(s) := SHA3-256(s)                        H : 𝔹* → 𝔹^32          (4.4)
J(s) := SHAKE256(s, 8·32)                  J : 𝔹* → 𝔹^32          (4.4)
G(c) := SHA3-512(c)                        G : 𝔹* → 𝔹^32 × 𝔹^32   (4.5)
PRF_η(s, b) := SHAKE256(s ‖ b, 8·64·η)     PRF : {2,3} × 𝔹^32 × 𝔹 → 𝔹^(64η)   (4.2, 4.3)
```

- `G` produces **two** 32-byte outputs: `(a, b) ← G(c)` where `G(c) = a ‖ b`. The first 32
  bytes come first — in Encaps that is `K`, in K-PKE.KeyGen that is `ρ`.
- **`η` in PRF is only an output length, not domain separation.** FIPS 203 says so
  explicitly: "Note that `η` is only used to specify the desired output length and not to
  perform domain separation." So `PRF_2` and `PRF_3` with the same `(s, b)` produce
  outputs where one is a prefix of the other. For η=2: **128 bytes out**.
- `H` and `J` both produce 32 bytes but are **different functions** — SHA3-256 vs
  SHAKE256. Swapping them is silent and fatal.
- Desired output length for SHAKE is specified **in bits** at the primitive level; the XOF
  wrapper takes bytes. See [`alg02-xof-incremental.md`](alg02-xof-incremental.md).

## §3.3 requirements — all normative ("shall")

### Randomness

> This RBG shall have a security strength of at least 128 bits for ML-KEM-512, at least
> **192 bits for ML-KEM-768**, and at least 256 bits for ML-KEM-1024.

The seeds shall be generated by the cryptographic module.

### Input checking

> Implementers **shall** ensure that ML-KEM.Encaps and ML-KEM.Decaps are only executed on
> inputs that have been checked, as described in Section 7.

See [`alg20-encaps.md`](alg20-encaps.md) and [`alg21-decaps.md`](alg21-decaps.md).

### Destruction of intermediate values — verbatim

> Data used in intermediate computation steps of KEM algorithms could be used by an
> adversary to compromise security. Therefore, implementers **shall ensure that
> intermediate data is destroyed as soon as it is no longer needed**. In particular, for
> ML-KEM.KeyGen, ML-KEM.Encaps, and ML-KEM.Decaps, **only the designated output can be
> retained in memory after the algorithm terminates. All other data shall be destroyed
> prior to the algorithm terminating.**

**Two exceptions, both explicit:**

1. The seed `(d, z)` from ML-KEM.KeyGen steps 1–2 **may be stored** for later expansion
   via KeyGen_internal. It "is sensitive data and shall be treated with the same
   safeguards as a decapsulation key."
2. The matrix `Â` **may be stored** — from K-PKE.KeyGen steps 3–7 and/or K-PKE.Encrypt
   steps 4–8. It "is data that is easily computed from the public encapsulation key and
   thus does not require any special protections."

Implementation consequence: wrap every stack-resident secret in `Zeroizing` (spec §8.3),
and `secure_zero` must not be elidable — verify by disassembly, not inspection.

### No floating-point arithmetic — verbatim

> Implementations of ML-KEM **shall not use floating-point arithmetic**, as rounding
> errors in floating-point operations may lead to incorrect results in some cases. In all
> pseudocode in this standard in which division is performed (e.g., `x/y`) and `y` may not
> divide `x`, either `⌊x/y⌋`, `⌈x/y⌉`, or `⌈x/y⌋` is used. All of these can be computed
> without floating-point arithmetic, as ordinary integer division `x/y` computes `⌊x/y⌋`,
> and `⌈x/y⌉ = ⌊(x + y − 1)/y⌋` for non-negative integers `x` and positive integers `y`.

### K-PKE is not approved standalone

> K-PKE is not approved for use in a stand-alone fashion. It serves only as a collection of
> subroutines for use in the algorithms of the approved scheme ML-KEM.

The K-PKE algorithms perform **no input checking** — they are only ever invoked as
subroutines of ML-KEM, which does the checking.

### The internal algorithms are test-only

> As prescribed in Section 3.3, the interfaces specified in this section [KeyGen_internal,
> Encaps_internal, Decaps_internal] **should not be made available to applications other
> than for testing purposes.**

Hence the `MLKEM_ENABLE_INTERNAL_API` build gate (spec §3.1): `make kat` defines it, the
default `make` does not.
